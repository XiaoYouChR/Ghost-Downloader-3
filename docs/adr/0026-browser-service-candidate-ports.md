# Browser Service 采用跨段候选端口池并分两步升级默认端口

Windows 下 Hyper-V 与 WSL（WinNAT）常在 `1024-15000` 及 `49152-65535` 区间按 100 个连续端口为一块保留端口，导致 Browser Service 的默认端口 `14370` 频繁因 `WSAEACCES` 无法绑定（#1028）。我们为 Browser Service 与浏览器扩展约定候选端口池 `[14370, 24370, 34370, 44370, 38370]`（分布在 `20000-45000` 安全区内且跨度远大于 100），并在桌面端与浏览器扩展两端同时提供默认开启的"自动选择端口"显式开关：开启时禁用手动端口/服务地址输入框（只读展示当前生效值），当首选端口冲突时 Port Listener 自动顺延绑定池中下一个可用端口并同步显示，扩展端在 150ms 内未连上首选地址或失败时对候选池发起并发竞速（Happy Eyeballs）并记忆胜出地址；关闭开关后则解锁手动输入，严格按用户指定的端口或地址监听与连接，冲突直接报错而不做隐式顺延。

过渡版本仍将 `14370` 留在候选池首位：未遇到冲突的存量用户升级后仍监听 `14370`，只会连 `14370` 的旧版自管理扩展得以连上并通过 `_onHello` 自动解包升级到支持候选池竞速的新版扩展，旧版商店扩展也不会在审核窗口期内断连；待存量扩展完成升级后，后续版本再将 `24370` 提为默认首选端口。

## Considered Options

- **一步到位直接把默认端口改为 `24370`**：否决。旧版扩展写死只连 `14370`，桌面端一旦立刻切走，存量自管理扩展无法完成 `hello` 握手触发 `reload` 自更新，商店版扩展在审核上架前也会全部失联。
- **连续递增试端口（`14370, 14371, ...`）**：否决。WinNAT 每次保留 100 个连续端口，小步长递增会落在同一个保留块内全部失败。
- **扩展端串行轮询候选端口**：否决。Windows 下连接未监听的本机端口单次超时可达 `500ms-2000ms`，串行轮询会造成配对与重连明显卡顿。
- **按"端口是否属于候选池"隐式决定是否自动顺延**：否决。违背 "Explicit is better than implicit"，用户在输入框看到固定端口号却被后台静默改写会产生困惑。
